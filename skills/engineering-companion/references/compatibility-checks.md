# Compatibility checks

Use these cases when an observed plugin change could affect the integration. They are evaluator guidance; hold the expected decisions back from a working agent. Give the worker an ordinary task, the companion, and the minimum raw context needed. Keep synthetic cases separate from claims about an actual application or plugin release.

| Task context | Decision to inspect |
| --- | --- |
| Only the personal global rule is supplied to a fresh-context resumed engineering task | Companion and applicable supplement recovered without a manual skill invocation; completed approvals retained |
| Managed and shared providers expose the same lifecycle skill; a spec and plan are already approved | Managed provider selected; completed stages retained; next actual requirement addressed |
| Managed entry is unprefixed and shared entry is prefixed after an update | Runtime provenance wins over name/prefix; no cache-version guessing |
| Current owner requires a plan, but only the specification is approved | Missing plan handled without repeating spec approval or skipping the new requirement |
| No managed provider is available; request is a narrow read-only explanation without delegation | Fallback disclosed; inline explanation; no installation or invented lifecycle dependency |
| Companion is re-entered inside review; current owner requires fresh task-specific tests | Review continues; required fresh test runs once; unrelated still-valid evidence retained |
| Two reviewers agree on a failure excluded by traced callers; one demonstrates a reachable failure | Actual evidence overrides vote counts; demonstrated issue remains actionable |
| DOM tests pass but an OTEF target-browser/hardware journey is inaccessible | Existing acceptance gate remains pending; no target-surface completion claim |

Inspect selected source paths, relevant reference reads, concrete findings, proposed/actual actions, and any resulting artifacts. A self-report of compliance is insufficient. Use disposable local state for authorized execution and preserve project restrictions. Do not enable background automation or remote jobs to run these checks.

Keep a short local record of case inputs, active provider/version, decisions, and limitations. Compare outcomes before expanding a trial. The initial companion passed simulated task/provider checks after ambiguity fixes; it has not established an improvement in production outcomes.
