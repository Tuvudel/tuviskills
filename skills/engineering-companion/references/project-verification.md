# Project verification

Use the active Superpowers verification requirement and the project's existing acceptance records. Verify the requested claim on the relevant surface; distinguish a passing check from a completed user journey.

## Use existing evidence and recipes

Read the current launch instructions, harnesses, and feature/acceptance documents. Establish the build and dataset identity, readiness, preconditions, and the scope/freshness of prior evidence. Reuse valid results for unchanged claims where the owner permits it. Run affected checks for changed behavior or unresolved gaps.

Drive the real supported path with the existing control, browser, terminal, or HTTP tooling. Capture the action and resulting state, and check relevant side effects. Isolate accounts, data, profiles, and ports as the project requires. Clean up only instances and scratch state created by the run; preserve evidence and unrelated sessions.

State precisely what was observed, what it proves, and what remains blocked or unverified. A healthy process does not establish loaded data, a DOM test does not establish projector readability, and setting a cross-origin window's URL does not prove its document loaded. Map results into existing acceptance records when an update is authorized; leave inaccessible hardware or account gates pending.

For a baseline/treatment claim, use `verify-this` when available and preserve comparable code, data, environment, and workload. A negative or inconclusive result remains useful.

## Create a recipe only when requested

If asked to author or repair a project verification skill, first inspect whether a useful recipe already exists. Extend its maintained source rather than create a competing checklist. Follow the project's permitted document/skill locations; the generator does not grant product-fix or publication authority.

A useful recipe records:

- Launch and usable readiness from the supported initial state.
- A read-only health check with build, instance, auth, and dataset identity.
- Exact user journeys, preconditions, stable selectors/commands, and observable outcomes.
- Evidence locations and what each proof does and does not establish.
- Owned-process cleanup that leaves the evidence intact.

Seed a small feature index only when the project lacks one. Exercise one supported journey through launch, health check, drive, capture, and cleanup before calling the generated recipe usable. Confirm the evidence survives cleanup. An unexecuted recipe is a draft; a stand-in environment leaves target-specific setup unverified.

Maintenance distinguishes outdated documentation, a harness gap, and a product regression. Correct docs/harness behavior only within authorized scope; report product failures rather than weaken acceptance to make the recipe pass.
